# Aenaon ERP — Βήμα 9.3: Φορολογικό μοντέλο καταλόγου (Design Gate)

## 1. Σκοπός

Το παρόν κλειδώνει τις **αρχιτεκτονικές προϋποθέσεις** πριν επεκτείνουμε τον κατάλογο ειδών με φορολογική πληροφορία. Υποστηρίζει από τον σχεδιασμό ΑΑΔΕ myDATA και πιστοποιημένο πάροχο ηλεκτρονικής τιμολόγησης **IMPACT / SoftOne Group**.

{% hint style="warning" %}
**Design-only:** αυτή η φάση δεν εισάγει πραγματικό μηχανισμό ΦΠΑ, εγκεκριμένους φορολογικούς συνδυασμούς, migration ή δυνατότητα έκδοσης παραστατικών. Η ένταξη κωδικών σε τεχνικό κατάλογο ΔΕΝ αποτελεί φορολογική πιστοποίηση. Οι νομικοί κανόνες και ο επιλεγμένος τρόπος διαβίβασης απαιτούν επιβεβαίωση πριν από ενεργοποίηση.
{% endhint %}

## 3. Κανόνες που απορρέουν από τις πηγές

1. `Product` / `Service` είναι επιχειρησιακός τύπος και **δεν επιβάλλει αυτομάτως ΦΠΑ ή χαρακτηρισμό**.
2. `VatCategoryCode` δεν ταυτίζεται με ποσοστό `VAT%`. Επιπλέον, η `vatExemptionCategoryCode` είναι χωριστό δεδομένο υπό προϋποθέσεις.
3. Οι χαρακτηρισμοί `ClassificationCategoryCode` και `ClassificationTypeCode` πρέπει να αξιολογούνται μαζί με τη φορολογική περίπτωση. Π.χ. η IMPACT δημοσιεύει `CATEGORY1_1`, `CATEGORY1_2`, `CATEGORY1_3` αλλά δεν επιτρέπουμε αυτόματη υπόθεση «κάθε Product=1_2».
4. Η IMPACT ζητά `Detail.MeasurementUnitCode` για σχετικές γραμμές, με εξαίρεση τιμολόγια υπηρεσιών σύμφωνα με τη σελίδα Minimum & Conditional Fields. Για B2G επιβάλλονται επιπλέον δεδομένα όπως `Detail.MeasurementUnitCodeEN`, `Detail.CpvCode` και στοιχεία σύμβασης.
5. `FNB` (προσωρινό έγγραφο παραγγελίας) δεν είναι νόμιμη φορολογική απόδειξη/τιμολόγιο, σε αντίθεση με την κατάλληλη φορολογική ροή `INVOICE`. Ο τελικός τύπος/myDATA κατηγορία επιλέγεται στο επίπεδο παραστατικού, όχι στην καρτέλα είδους.
6. Το πληρωτέο ποσό, καθαρή αξία, ΦΠΑ, εκπτώσεις και σύνολα υπολογίζονται ανά **γραμμή παραστατικού / συγκεκριμένη πράξη** με επαληθευμένους κανόνες και συνεπές `decimal`, όχι από απλή στατική ετικέτα του είδους.

## 4. Προτεινόμενη αρχιτεκτονική — χωρίς ακόμη εφαρμογή

### Catalog — σταθερή εμπορική ταυτότητα

Το υπάρχον `CatalogItem` διατηρεί `TenantId`, `Id`, `CategoryId`, `Code`, `Name`, `Kind`, `TracksStock`, `IsActive`. Δεν αποθηκεύουμε ως μοναδική αλήθεια ούτε τον «μόνιμο ΦΠΑ» ούτε τον τύπο παραστατικού σε αυτά τα πεδία.

### FiscalReferenceData — versioned λεξικά

Εσωτερικές οντότητες / πίνακες αναφοράς με `Source` (AADE/IMPACT), `CodeSystem`, `Code`, `Description`, `EffectiveFrom`, `EffectiveUntil`, `SourceVersion` και ημερομηνία επαλήθευσης. Ένα API code αναγνωρίζεται μόνο από το σωστό code system, όχι από το σκέτο «1»/«2».

### FiscalProfile — προτεινόμενες ρυθμίσεις ανά Tenant

Χρειάζονται ισχυροί έλεγχοι σε κάθε ανάθεση: `TenantId`, `CatalogItemId`, κατάσταση/ημερομηνία ισχύος, προεπιλεγμένη εσωτερική φορολογική μεταχείριση, προτεινόμενη μονάδα, τυχόν εξαιρέσεις, καθώς και audit αλλαγών.

**Δεν αποφασίζουμε ακόμη** αν απαιτείται επέκταση ανά `StoreId`, φορολογικό κανάλι, κατηγορία πελάτη, χώρα, απαλλαγή ή ειδικό καθεστώς. Οι διαστάσεις αυτές είναι είσοδοι του μηχανισμού επίλυσης και όχι σιωπηρές τιμές.

### TaxResolutionContext — κρίση κατά τη συναλλαγή

Προτείνεται immutable snapshot context:
- `TenantId`, `StoreId`, ημερομηνία συναλλαγής,
- `CatalogItemId`, `CatalogItemKind`, ποσότητα, μονάδα μέτρησης,
- προτεινόμενος/επιλεγμένος τύπος παραστατικού και κανάλι (`B2C`, `B2B`, `B2G`, F&B, διακίνηση),
- στοιχεία φορολογικής κατάστασης λήπτη και τόπου συναλλαγής, όπου απαιτούνται,
- εφαρμοστέα έκδοση φορολογικών κανόνων.

### FiscalResolution — αποτέλεσμα ή ρητή απόρριψη

Δεν επιτρέπεται silent fallback σε 24%, 0% ή κενή ταξινόμηση. Ο μηχανισμός επιστρέφει είτε **επικυρωμένη πρόταση** με τεκμηριωμένη πηγή κανόνων είτε **αναγνωρίσιμο σφάλμα**, ώστε να μη δημιουργηθεί άκυρο παραστατικό.

## 5. Μελλοντικό mapping: αποδεικτική αντιστοίχιση

| Aenaon conceptual field | ΑΑΔΕ / IMPACT | Επαλήθευση |
| --- | --- | --- |
| Επιλεγμένο φορολογικό έγγραφο | `documentTypeCode`, `invoiceTypeCode` | Ανά τύπο / κανάλι / ροή |
| Αναφορά γραμμής είδους | `Detail.Code` / `Detail.ItemCodification` | Επιβεβαίωση αν/πότε απαιτείται |
| Ποσότητα και μονάδα | `Detail.Quantity`, `Detail.MeasurementUnitCode` | Τύπος παραστατικού και αγαθό/υπηρεσία |
| Μονάδα EN16931 | `Detail.MeasurementUnitCodeEN` | B2G / ειδική ροή |
| Φορολογική κατηγορία | `Detail.VatCategoryCode` | Με ενεργή κατηγορία και κατάλληλο ποσοστό |
| Αιτία απαλλαγής | `Detail.VatExemptionCategoryCode` | Μόνο όπου επιβάλλεται |
| Χαρακτηρισμοί | `Detail.IncomeClassification` | Συνδυασμοί myDATA / παραστατικό |
| Φορολογική αξία | `Detail.NetTotal`, `Detail.VatTotal` | `decimal`, στρογγυλοποίηση / έκπτωση |
| Σύνολα παραστατικού | `Summaries.TotalNetAmount`, `TotalVatAmount`, `TotalGrossValue` | Συμφωνία με γραμμές και φόρους |

*Τα ονόματα αφορούν τεκμηρίωση της IMPACT· το ακριβές JSON casing θα παράγεται από ελεγμένο adapter/OpenAPI, όχι από την απλή στήλη του πίνακα.*

## 6. Κριτήρια σχεδιασμού πριν από κώδικα και migration

- [ ] Επιβεβαιώνουμε την πραγματική φορολογική ροή εκδότη μέσω **IMPACT certified provider**, χωρίς παράλληλη/διπλή διαβίβαση myDATA από άλλο κανάλι.
- [ ] Καταγράφουμε ρητά αρχικό εύρος: B2C πωλήσεις εστίασης, B2C υπηρεσίες, B2B αγαθά/υπηρεσίες· B2G/ενδοκοινοτικές/εξαγωγές ως ξεχωριστές ενεργοποιήσεις.
- [ ] Ορίζουμε δεσμευτική πολιτική ΦΠΑ για πραγματικές περιπτώσεις, όχι αυθαίρετες τιμές ανά `Product`/`Service`.
- [ ] Διακρίνουμε rate, VAT category code και exemption code· ορίζουμε ημερομηνίες ισχύος.
- [ ] Επιβεβαιώνουμε τους έγκυρους **συνδυασμούς** εσόδων και τους αντίστοιχους `E3_...` χαρακτηρισμούς.
- [ ] Επιβεβαιώνουμε μονάδες μέτρησης και conditional fields ανά εκδιδόμενο τύπο παραστατικού.
- [ ] Ορίζουμε immutable snapshot στις φορολογικές γραμμές, audit και σχέδιο τροποποίησης μετά από έκδοση.
- [ ] Ορίζουμε πλήρες test matrix (B2C/B2B/B2G, zero/exempt, έκπτωση, ακύρωση, επιστροφή, offline).
- [ ] Η τελική σύμβαση IMPACT / staging credentials επαληθεύεται χωρίς αποστολή πραγματικών δεδομένων.
- [ ] Κάθε PR δηλώνει ποιες επίσημες σελίδες/εκδόσεις επανελέγχθηκαν.

## 7. Παράδοση του παρόντος βήματος

Αυτό το PR παραδίδει **επιθεωρημένο design contract και checklist**, όχι runtime υλοποίηση. Η συνέχεια χωρίζεται σε δύο ελεγχόμενες παραδόσεις:

1. **9.3A — Fiscal Domain contracts & tests**: immutable reference types / rule validation χωρίς DB ή εξωτερικές κλήσεις· υλοποίηση μόνο μετά από review του παρόντος.
2. **9.3B — Fiscal persistence / mappings**: νέα migration, tenant-safe constraints, ελεγχόμενη ενημέρωση λεξικών και SQL integration tests. Χωρίς αυτόματη έκδοση.
3. **9.4 — Back Office UI**: CRUD ειδών και ξεχωριστές καρτέλες προτεινόμενων φορολογικών ρυθμίσεων με `Owner` access.

## 8. Τι ΔΕΝ ισχυρίζεται η υλοποίηση

Δεν αποδίδεται «πιστοποιημένο ERP», δεν υπολογίζεται νόμιμος ΦΠΑ από αυτά τα έγγραφα, δεν υπάρχουν παραστατικά ή MARK και δεν έχει γίνει κλήση στο IMPACT. Η παραγωγική φορολογική συμβατότητα θα επιβεβαιωθεί με **δοκιμές συμβολαίου και επιχειρησιακής ροής** όταν ολοκληρωθούν οι αντίστοιχες υλοποιήσεις.
