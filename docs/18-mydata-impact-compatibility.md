# Aenaon ERP — Υποχρεωτική συμβατότητα ΑΑΔΕ myDATA & IMPACT

## 1. Σκοπός και ισχύς

Αυτό το έγγραφο αποτελεί **οριζόντια, υποχρεωτική αρχιτεκτονική προδιαγραφή** για κάθε σχετική λειτουργία του Aenaon ERP — Back Office, POS εστίασης, Android παραγγελιοληψία, αποθήκη, πληρωμές, φορολογικά παραστατικά, offline κόμβο και συγχρονισμό.

**Κανόνας:** καμία λειτουργία που μεταβάλλει φορολογικά δεδομένα ή επηρεάζει έκδοση/διαβίβαση δεν χαρακτηρίζεται ολοκληρωμένη χωρίς έλεγχο της ισχύουσας έκδοσης ΑΑΔΕ myDATA **και** του επίσημου συμβολαίου IMPACT. Οι εκδόσεις και τα API συμβόλαια πρέπει να επανεξετάζονται κατά την υλοποίηση, όχι να θεωρούνται σταθερά.

{% hint style="warning" %}
Η ύπαρξη σωστών Domain models, SQL πινάκων ή επιτυχούς CI **δεν αποδεικνύει αυτομάτως φορολογική/νομική συμμόρφωση**. Η τελική διασύνδεση απαιτεί ελέγχους έναντι XSD, provider payloads, συμφωνημένης ροής παρόχου και του ισχύοντος κανονιστικού πλαισίου.
{% endhint %}

## 3. Καθολικό checklist συμβατότητας ανά αλλαγή

Πριν σχεδιαστεί ή γίνει merge σχετική λειτουργία:

1. Καταγράφουμε **ποια έκδοση** myDATA / IMPACT ισχύει, πότε ελέγχθηκε και ποιες ακριβώς ενότητες τη στηρίζουν.
2. Κατατάσσουμε τη ροή (B2B, B2C, B2G, αγαθό, υπηρεσία, διακίνηση, επιστροφή, ακύρωση, πιστωτικό, πληρωμή).
3. Ελέγχουμε **τύπο παραστατικού, σειρά/αριθμό, ημερομηνία, εκδότη, λήπτη, ΦΠΑ, αιτία απαλλαγής, χαρακτηρισμούς, κρατήσεις/τέλη και κανόνες στρογγυλοποίησης** όπου εφαρμόζονται.
4. Ελέγχουμε απαιτήσεις/εξαιρέσεις για **γραμμές παραστατικών**, ποσότητες, μονάδες μέτρησης, τιμή, εκπτώσεις, φόρους και σύνθεση συνόλων.
5. Διατηρούμε τα **επιχειρησιακά φορολογικά δεδομένα** στο δικό μας Domain/Application και εφαρμόζουμε τα IMPACT/myDATA codes σε καθορισμένο mapping layer. Δεν κωδικοποιούμε άκριτα vendor enum/string τιμές σε άσχετα Domain μοντέλα.
6. Στη στιγμή έκδοσης κρατάμε **αμετάβλητο snapshot** των ουσιωδών στοιχείων της συναλλαγής. Αλλαγή στην καρτέλα είδους δεν πρέπει να μεταβάλλει εκδοθέν παραστατικό.
7. Αποθηκεύουμε και συμφιλιώνουμε κατάσταση διαβίβασης, επιστρεφόμενους αναγνωριστικούς αριθμούς (π.χ. MARK, UID όπου προβλέπεται), στοιχεία πιστοποίησης/QR/URL και κωδικούς λαθών χωρίς να αποκρύπτουμε αποτυχίες.
8. Σχεδιάζουμε **idempotency/anti-duplicate**, ειδικά για timeout, άγνωστη απάντηση, retry, offline κατάσταση και επανασύνδεση. Πριν από πιθανή επαναποστολή ελέγχουμε τη διαθέσιμη ροή συμφιλίωσης του παρόχου.
9. Χρησιμοποιούμε διαχωρισμένα test/production credentials και endpoints, TLS, ελάχιστα δικαιώματα, προστατευμένη αποθήκευση secrets και logging χωρίς προσωπικά/φορολογικά μυστικά.
10. Προσθέτουμε automated tests με επιβεβαιωμένα **μη πραγματικά** fixtures, schema/contract validation, αρνητικά σενάρια και, όπου είναι εφικτό, ελεγχόμενες δοκιμές στο επίσημο sandbox.

## 4. Συνέπειες για τον κατάλογο ειδών (Βήματα 9.1–9.3)

Το υπάρχον `CatalogItemKind = Product | Service` αποτυπώνει **μόνο επιχειρησιακή διάκριση είδους** και τον κανόνα αποθέματος. **Δεν καθορίζει αυτόματα**:

- συντελεστή ΦΠΑ ή φορολογική κατηγορία,
- τύπο παραστατικού,
- χαρακτηρισμό myDATA,
- αιτία απαλλαγής/ειδικό φορολογικό καθεστώς,
- ειδική κατάταξη ανά είδος συναλλαγής, πελάτη ή κανάλι,
- μονάδα μέτρησης/κωδικό μονάδας για συγκεκριμένο provider payload,
- υποχρεωτικά πεδία παρόχου για διακίνηση, POS, F&B ή B2G.

Αυτά θα προστεθούν σε **ρητά σχεδιασμένες επόμενες ενότητες** (π.χ. φορολογικό προφίλ, αντιστοίχιση myDATA, πολιτική ανά τύπο παραστατικού, αμετάβλητη γραμμή παραστατικού), αφού επιβεβαιώσουμε την ακριβή προδιαγραφή. Αποφεύγουμε να αποθηκεύσουμε αυθαίρετα την τιμή `vatCategory` ή κωδικούς IMPACT ως δήθεν καθολικά πεδία όλων των ειδών χωρίς μελέτη.

**Εκτίμηση για migration 9.2:** οι πίνακες `CatalogCategories`/`CatalogItems` και ο κανόνας υπηρεσιών/αποθέματος δεν προϋποθέτουν ούτε πραγματοποιούν διαβίβαση. Είναι θεμέλιο καταλόγου, **όχι πλήρης φορολογική υλοποίηση**. Κάθε φορολογική προσθήκη στο schema θα γίνει με νέα versioned migration, όχι με σιωπηρή τροποποίηση ήδη εφαρμοσμένης.

## 5. Σχέδιο διασύνδεσης IMPACT (χωρίς ενεργές κλήσεις)

Η δημόσια τεκμηρίωση περιγράφει, μεταξύ άλλων, `POST /Invoice/json`, `POST /Invoice/credit`, `POST /Invoice/Void/{publicSignature}`, `POST /Invoice/updatePayment` και `GET /FnBDocuments/{issuerTin}/open`. Οι ακριβείς προϋποθέσεις, η διαθεσιμότητα κάθε λειτουργίας και η πραγματική ροή επιβεβαιώνονται ανά συμβόλαιο και έκδοση.

Προτεινόμενη αρχιτεκτονική (εφαρμόζεται **σε επόμενο βήμα**, όχι τώρα):

- `Domain`: εσωτερικά, provider-neutral μοντέλα ειδών, φόρων, γραμμών και παραστατικών.
- `Application`: validation, fiscal policy, εξουσιοδότηση, idempotency, lifecycle, audit και συμφιλίωση.
- `Infrastructure`: ειδικός `ImpactInvoiceProviderClient`, DTOs/adapters με βάση την επίσημη έκδοση OpenAPI, HTTPS και ασφαλές credential handling.
- `Persistence`: αμετάβλητο invoice snapshot, παρακολούθηση αιτήματος/απάντησης και retry state χωρίς διπλοέκδοση.
- `UI/CLI`: ρητή επιβεβαίωση πραγματικής έκδοσης, σαφής κατάσταση, ορατά σφάλματα, ασφαλές retry ή χειροκίνητη συμφιλίωση.

**Απαγόρευση:** καμία αυτόματη πραγματική έκδοση ή ακύρωση παραστατικού πριν ολοκληρωθούν οι έλεγχοι συμβατότητας, το sandbox testing και η επιχειρησιακή έγκριση.

## 6. Εστίαση, POS, offline και διακίνηση

Η IMPACT περιλαμβάνει ειδικά κεφάλαια F&B, POS integration, offline QR, ψηφιακή διακίνηση, IRIS και B2G. Η ΑΑΔΕ v2.0.2 τεκμηριώνει χωριστά τα κανάλια ERP/παρόχων και τις πρόσφατες μεταβολές στη διακίνηση.

Συνεπώς **η offline παραγγελιοληψία δεν σημαίνει αυτομάτως ότι επιτρέπεται offline έκδοση φορολογικού παραστατικού**. Η δυνατότητα, οι χρονισμοί, τα QR/υπογραφές και ο συγχρονισμός πρέπει να καλύπτονται από συγκεκριμένη έγκυρη ροή.

Διαχωρίζουμε πάντοτε:
- `Order`: επιχειρησιακή παραγγελία σε τοπικό ή cloud κόμβο.
- `FiscalDocument`: φορολογικό παραστατικό με υποχρεωτικό lifecycle και ίχνος ελέγχου.
- `ProviderSubmission`: κλήση IMPACT/ΑΑΔΕ, ενδεχόμενη αβέβαιη έκβαση και τελική συμφιλίωση.
- `StockMovement` / `DeliveryNote`: διακίνηση αγαθών και αντίστοιχες απαιτήσεις.

## 7. Κριτήρια ολοκλήρωσης (Definition of Done)

Ένα PR που επηρεάζει φορολογική/τιμολογιακή λειτουργία θεωρείται έτοιμο **μόνο εφόσον**:

- [ ] Έχει τεκμηριωμένες επίσημες πηγές, έκδοση και ημερομηνία ανάγνωσης.
- [ ] Διαθέτει πίνακα αντιστοίχισης εσωτερικών πεδίων με myDATA/IMPACT.
- [ ] Έχει αναγνωρισμένα required/conditional fields, ανά τύπο παραστατικού.
- [ ] Έχει ελέγχους φόρων, συνόλων, εκπτώσεων, στρογγυλοποίησης και χαρακτηρισμών.
- [ ] Καλύπτει διπλή αποστολή, timeout, offline/retry, ακυρώσεις/πιστωτικά όπου εφαρμόζεται.
- [ ] Καλύπτει tenant isolation, authorization, logging, secrets και προσωπικά δεδομένα.
- [ ] Έχει ολοκληρωθεί test με κατάλληλα fixtures/sandbox και δεν χρησιμοποιήθηκαν πραγματικές εγγραφές πελατών.
- [ ] Έχουν επισημανθεί τυχόν μη καλυπτόμενα σενάρια πριν από το merge.
- [ ] Έχει επικαιροποιηθεί το ελληνικό user/technical manual.

## 8. Τρέχουσα κατάσταση και επόμενη εργασία

- **9.1:** in-memory μοντέλο καταλόγου — ολοκληρωμένο ως Domain foundation, όχι φορολογικό engine.
- **9.2:** SQL schema καταλόγου — έτοιμη migration, αλλά απαιτεί ξεχωριστό backup/review/apply στη `AenaonERP_Dev`.
- **9.3 (πριν από φόρμες φορολογικών ρυθμίσεων):** σχεδιασμός φορολογικού προφίλ ειδών και αντιστοιχίσεων myDATA/IMPACT, υποστηριζόμενων τύπων παραστατικών και δεδομένων μονάδας μέτρησης.
- **Επόμενη φάση έκδοσης:** συμβόλαια φορολογικών παραστατικών, provider adapter, δοκιμαστικό περιβάλλον και idempotent submission state machine.

Εφόσον οι προδιαγραφές αλλάζουν, επαναλαμβάνουμε τους ελέγχους των επίσημων πηγών πριν από κάθε φορολογικά σημαντική υλοποίηση.
